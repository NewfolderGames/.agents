# 한국어 기술 문서 및 코드 문서화 스타일 가이드

본 가이드는 [전자정부 표준프레임워크 가이드 문서 저장소(eGovFramework/egovframe-docs)](https://github.com/eGovFramework/egovframe-docs)의 문장 구성 스타일 가이드, 실행환경·공통컴포넌트 문서 패턴, 문서 정합성 점검 기준(`docs_lint.py`)을 바탕으로 정리한다. 대상 저장소가 별도의 한국어 문서 컨벤션을 정의한 경우 대상 저장소의 규칙을 우선한다.

---

## 1. 문체와 어조

### 1.1 문체 원칙

1. **일관된 공식 문어체 평서형 사용**: 본문, 기술 설명, 주석은 공식 문어체 평서형(`~한다`, `~이다`, `~제공한다`, `~의미한다`, `~사용한다`)으로 통일한다.
2. **격식과 신뢰감 유지**: 구어체(`~해요`, `~거든요`), 감탄 표현, 명령조(`~해라`, `~하라`)를 사용하지 않는다. 절차나 설정 안내에서도 명령조 대신 서술형(`~를 추가한다`, `~로 설정한다`, `~을 실행한다`)으로 작성한다.
3. **단문 중심의 명확하고 간결한 문장**: 복잡한 개념은 짧은 문장으로 나누어 설명하며, 가능한 한 간단하게 표현한다.
4. **동일한 어휘와 문체 유지**: 한 문서 안에서 경어체(`~합니다`)와 평서체(`~한다`)를 섞지 않고, 동일한 개념에는 하나의 용어만 일관되게 사용한다.
5. **이중 피동과 번역투 회피**: `관리되어지는`, `호출되어진다`, `적용되어 있다` 같은 이중 피동이나 장황한 표현 대신 `관리되는`, `호출된다`, `적용된다`처럼 간결한 능동 또는 단일 피동을 사용한다.

### 1.2 어조 원칙

1. **사실 기반의 객관적·중립적 어조**: 주관적인 의견, 과장, 감정적 수식을 배제하고 확인된 동작과 사실만 서술한다.
2. **교육적이고 안내하는 어조**: 독자가 개념과 적용 절차를 단계적으로 이해할 수 있도록 목적, 원리, 사용 예시 순서로 안내한다.
3. **제약 사항과 부작용의 명시**: 전역 설정 변경이 미치는 영향 범위, 세션 간섭 가능성, 재시작 불가 조건 등 운영상 주의가 필요한 사실은 생략하지 않고 명시한다.

### 1.3 기준 예시

다음은 [eGovFramework/egovframe-docs](https://github.com/eGovFramework/egovframe-docs)에서 제시하는 공식 문체 예시이다.

- "Inversion of Control(역제어)은 객체의 생성 및 생명주기 관리를 개발자가 아닌 컨테이너가 담당하는 것을 의미한다."
- "Spring Framework의 IoC Container는 다양한 기능을 제공하며, 이를 통해 애플리케이션의 유연성과 확장성을 향상시킬 수 있다."
- "의존성 주입(Dependency Injection)은 빈 설정 정보를 바탕으로 컨테이너가 클래스 간의 의존 관계를 자동으로 연결해주는 방법이다."

### 1.4 문체 교정 대비표

| 지양 표현 | 권장 표현 | 이유 |
|---|---|---|
| `설정 파일을 열어 값을 바꿔주세요.` / `값을 바꿔라.` | `설정 파일에서 해당 항목의 값을 변경한다.` | 경어체·명령조 대신 공식 문어체 평서형을 유지한다. |
| `IoC Container에 의해 관리되어지는 객체이다.` | `IoC Container가 관리하는 객체이다.` | 이중 피동을 제거하고 주어를 명확히 드러낸다. |
| `이 기능은 매우 강력하며 개발 생산성을 혁신적으로 높여준다.` | `이 기능은 공통 로깅과 트랜잭션 처리를 분리하여 비즈니스 로직의 중복 코드를 줄인다.` | 주관적 과장을 제거하고 사실 기반의 효과를 제시한다. |
| `좁은 연결-밸브를 적용하면 밸브-유발 대기 지연이 발생한다.` | `커넥션 풀 크기를 50에서 10으로 줄이면 요청 대기 시간이 늘어난다.` | 정의 없는 임의 합성어 대신 기존 도메인 용어와 평이한 동사를 사용한다. |

## 2. 기술 용어 표기와 코드 식별자

1. **첫 사용 시 원어 병기와 정의**: 핵심 영문 기술 용어나 약어는 문서에서 처음 등장할 때 한글 번역과 원어(또는 약어)를 함께 표기하고 간결하게 정의한다.
   - 예: `제어의 역전(Inversion of Control, IoC)`, `의존성 주입(Dependency Injection, DI)`, `이중등록(Double Submit)`, `LLM(Large Language Model)`
2. **문서 내 외래어·약어 표기 통일**: `메서드`/`메소드`, `애플리케이션`/`어플리케이션`, `디렉터리`/`디렉토리`, `IoC 컨테이너`/`IoC Container`처럼 혼용하기 쉬운 표기는 대상 저장소의 기존 표기를 따르거나 한 문서 안에서 하나로 고정한다.
3. **코드 식별자 원문 유지**: 클래스명, 메서드명, 패키지 경로, 설정 키, XML 태그명, CLI 플래그는 번역하지 않고 백틱(`` ` ``)으로 감싸 원문 그대로 표기한다.
   - 예: `` `ChatClient.Builder` ``, `` `EgovDoubleSubmitHelper.checkAndSaveToken()` ``, `` `context-properties.xml` ``

## 3. 표준 문서 구조 및 템플릿

제목은 최상위 문서 제목에 H1(`#`)을 한 번만 사용하고, 하위 섹션은 `H1 -> H2 -> H3 -> H4` 순서대로 레벨을 건너뛰지 않고 구성한다.

### 3.1 개념 및 아키텍처 문서 구조

프레임워크 원리, 아키텍처 개요, 설계 가이드를 작성할 때 사용한다.

```markdown
# [문서 제목]

## 개요
문서의 목적, 적용 범위, 핵심 기능을 1~2개의 완결된 문장으로 요약한다.

## 주요 개념
### [개념 1]
개념 1의 정의와 역할을 설명한다. 첫 사용 시 영문 원어 또는 약어를 병기한다.

### [개념 2]
개념 2의 정의와 역할을 설명한다.

## 관련 문서
- [문서 제목 1](./relative-doc.md)
- [외부 공식 문서](https://example.com/docs)

## 설명
핵심 동작 원리와 세부 구조를 하위 섹션(`###`, `####`)으로 나누어 체계적으로 설명한다.

## 참고자료
- [참고자료 1](https://example.com/reference)
```

### 3.2 코드 및 컴포넌트 구현 가이드 구조

실제 모듈, 라이브러리, 공통 컴포넌트, API 사용법을 문서화할 때 사용한다. 설정이나 참고자료가 없는 경우 해당 섹션을 생략하거나 `해당 없음`으로 명시한다.

```markdown
# [컴포넌트 또는 모듈명]

## 개요
해당 컴포넌트가 해결하는 문제와 제공하는 기능을 1~2문장으로 요약한다.

## 설명
동작 원리를 간결히 설명한다. 상태 전이나 호출 흐름이 복잡하면 Mermaid `flowchart`를 추가한다.

### 관련 소스

| 유형 | 대상 소스 | 설명 | 비고 |
|---|---|---|---|
| Controller | `pkg.web.ExampleController.java` | 요청 처리 컨트롤러 | |
| Service | `pkg.service.ExampleService.java` | 비즈니스 로직 인터페이스 | |
| Util | `pkg.util.ExampleHelper.java` | 공통 유틸리티 클래스 | |

## 환경 설정
필수 런타임 버전, DDL/DML, XML/YAML 설정 예시를 제시한다.

## 사용 방법
주요 메서드·옵션 표와 실행 가능한 코드 예시를 제시한다. 기존 코드를 수정하는 절차는 변경 전/변경 후로 대비한다.

### 주의 사항 및 제약
전역 영향 범위, 동시성 제약, 다중 세션 간섭 등 운영 시 유의할 동작을 명시한다.

## 참고자료
- [관련 공식 문서](https://example.com/spec)
```

## 4. 코드 예시, 표, 다이어그램 및 링크 규칙

### 4.1 코드 블록과 해설

1. **언어 태그 지정**: 모든 코드 블록은 삼중 백틱 뒤에 언어명(`java`, `xml`, `yaml`, `sql`, `bash`, `json` 등)을 명시한다.
2. **앞뒤 요약 연결**: 코드 블록 바로 앞에서 해당 코드의 목적을 1문장으로 설명하고, 코드 블록 뒤에서 주요 메서드·옵션·설정을 불릿 목록으로 정리한다.
   - 예:
     - `` `prompt()` ``: 프롬프트 빌더 시작
     - `` `user()` ``: 사용자 메시지 설정
     - `` `call()` ``: 모델 호출
     - `` `content()` ``: 응답 문자열 반환
3. **변경 전 / 변경 후 대비**: 기존 코드에 기능을 연동하거나 마이그레이션하는 경우 `변경 전`과 `변경 후` 두 코드 블록으로 대비하여 추가·수정된 라인을 명확히 보여준다.

### 4.2 구조화 표 활용

반복되는 클래스 목록, API 명세, 요구사항, 매핑 정보는 산문 대신 표준 표로 정리한다.

| 용도 | 권장 컬럼 구성 |
|---|---|
| 관련 소스 목록 | `유형 \| 대상 소스 \| 설명 \| 비고` |
| 메서드·API 명세 | `반환 타입 \| 메서드명 \| 설명 \| 비고` |
| 시스템 요구사항 | `소프트웨어 \| 버전 \| 용도` |
| 엔드포인트·액션 매핑 | `Action \| URL \| Controller method \| QueryID` |
| 관련 테이블·코드 | `테이블명 \| 테이블명(영문) \| 비고` |

### 4.3 다이어그램, 이미지, 파일명, 링크

1. **흐름도 작성**: 호출 순서나 분기 로직은 간결한 Mermaid `flowchart LR` 또는 `flowchart TD`로 표현한다.
2. **이미지 경로와 대체 텍스트**: 이미지 파일은 문서와 같은 디렉터리 하위의 `images/` 폴더에 저장하고, 구조를 설명하는 대체 텍스트(`![IoC Container 구조](./images/ioc-container-structure.png)`)를 작성한다.
3. **파일명 규칙**: 파일명은 문서 주제를 간결히 나타내는 소문자와 하이픈(`kebab-case`, 예: `ioc-container.md`)으로 작성한다.
4. **링크 경로 구분**: 외부 문서는 절대 경로(`https://...`)를 사용하고, 내부 문서는 실제 물리 파일 위치 기준의 상대 경로를 사용한다.
5. **위험 및 주의 표기**: 데이터 손실, 잠금, 전역 설정 영향 등 주의가 필요한 단계 앞에는 `WARNING:` 또는 `CAUTION:`(또는 프로젝트 컨벤션에 맞는 `[주의]`)을 배치하고 조건과 결과를 먼저 적는다.

## 5. 문서 정합성 점검 체크리스트

문서 작성이나 수정을 마친 뒤 다음 항목을 점검한다.

- [ ] **완결된 요약 문장**: 문서 개요와 목차 요약이 말줄임표(`…`)로 잘리지 않고 마침표(`.`)로 완결된다.
- [ ] **문체와 어조 통일**: 문서 전체가 공식 문어체 평서형(`~한다 / ~이다`)과 객관적·안내적 어조로 일관되며, 구어체·명령조·이중 피동·과장 표현이 없다.
- [ ] **용어 정의와 일관성**: 핵심 영문 용어와 약어를 첫 사용 시 정의하고, 동일 개념에 하나의 표기만 사용한다.
- [ ] **제목 계층과 상대 링크**: 제목 레벨을 건너뛰지 않으며(`H2 -> H4` 금지), 모든 내부 상대 링크가 실제 파일과 일치한다.
- [ ] **소스 코드 정합성**: 본문, 표, 코드 블록에 표기한 클래스명, 메서드명, 파일 경로, 설정 키가 실제 코드베이스와 일치한다.
